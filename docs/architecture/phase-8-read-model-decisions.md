# Phase 8 read-model decisions

- `GET /api/v1/dashboard/overview`, `GET /api/v1/student-registry`, and `GET /api/v1/students/{student_id}/profile` are authenticated reads for all three roles. They do not replace normalized APIs.
- Readiness uses the canonical 30-feature specification (`PREDICTION_FEATURES`). The dashboard and registry filter generate SQL checks from its storage mappings and validation bounds; displayed registry/profile readiness uses `assemble_prediction_features` on eagerly loaded domain rows.
- A student's latest prediction is ordered by `predicted_at DESC, id DESC`. Risk distribution counts that prediction once. A current registry warning must link to that prediction. The profile active warning is its non-dismissed warning; older warnings remain history only.
- Dashboard `warnings.active` counts every persisted warning whose current `review_state` is not `DISMISSED`. State counts describe current rows, while `warning_activity` counts persisted creations and individual review records. Multiple reviews can contribute multiple events on different dates.
- Dashboard intervention `active` counts `PLANNED`, `IN_PROGRESS`, and `ACTION_REQUIRED`. Follow-up `due_today` and `overdue` count only stored `SCHEDULED` rows using Phase 7 UTC calendar-day boundaries.
- Dashboard activity includes days with persisted events in a 14-day UTC window (today and 13 preceding days). No zero-filled days or inferred status transitions are added. `last_import_at` is the maximum `completed_at` of successful (`IMPORTED`) import jobs; failed/in-progress uploads are excluded.
- Registry interventions are selected only from the warning linked to the latest prediction. Active statuses rank `ACTION_REQUIRED`, `IN_PROGRESS`, then `PLANNED`; terminal cases follow. Ties use newest `created_at`, then highest UUID. Case owner comes from this intervention's assignee when it is active, otherwise the current warning assignee.
- Registry `approval_rate` is null when enrolled units are zero. `last_activity_at` is the maximum persisted student update, prediction, warning create/update/review, intervention create/update/note, or follow-up create/complete timestamp.
- The timeline orders persisted events by timestamp descending. Intervention and follow-up cancellation use persisted `updated_at` from their terminal cancellation writes. No event is inferred for intermediate `IN_PROGRESS` or `ACTION_REQUIRED` changes because their transitions are not separately stored.
- Category labels are centralized in `app.utils.category_labels`; unknown codes display their string representation. Codes remain in responses and ML inputs are untouched.
- Registry pagination and filtering happen in SQL. Latest prediction and current intervention use window queries. The page fetches related domain rows in a bounded number of bulk queries; profile uses a bounded number of targeted queries.
- No migration was needed. Both optional CSV export endpoints are deferred; the three core read models are the Phase 8 deliverable.
